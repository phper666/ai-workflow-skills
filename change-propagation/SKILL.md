# 变更传播

执行工作流步骤 11：上游共识规则变化 → 影响显性化 → 下游收敛 → 复核闭环。**原则：先影响分析，再分级处理，不是全量直接改。**

## Phase 1：变更摘要

1. 定位变更：读取共识文档变更记录 / `docs/spec/变更摘要` 最新一条
2. 提取：规则编号、旧结论、新结论、生效时间、变更人
3. 变更摘要缺失 → 按 `references/模板-变更摘要.md` 生成（问清旧/新结论）

## Phase 2：影响定位

沿规则编号找引用（AI 做，人确认）：

- `docs/api/` 契约文档中引用该规则编号的接口/场景
- 子需求（PM 工具）绑定该规则编号的条目
- 测试场景（契约"联调与测试场景"表 / QA 测试矩阵）
- 其他共识文档交叉引用（跨模块）
- 引用缺失/编号未登记 → 退化为全量通知 + 人工确认影响清单（不建图谱系统）

## Phase 3：分级处理

| 变更类型 | 处理 |
|:---------|:-----|
| 纯语义跟随（字段/规则描述变化，无争议，不破坏兼容） | **AI 直接自动更新**受影响契约（按 story-to-contract 的幂等更新语义，不产生 -v2 副本） |
| 破坏兼容（接口路径/字段删除、类型变化） | 等责任人确认（受影响契约的经办人），列兼容影响说明 |
| 涉及权限 / 数据 / 资金 / 状态机 / 事务 / 隔离 | 等责任人确认，先改共识再改契约的顺序强制 |
| 跨模块 | 列协调事项 + 责任人 + 截止时间 |

- 责任人 = 受影响契约/ticket 的经办人（查 `docs/spec/团队配置.md` 角色映射）；无经办人 → 标"无负责人"交 PM 指派
- 只有被引用到的模块的责任人介入，**不是全员**；灵活调配团队中一人可负责多模块

## Phase 4：重跑编排（不复制逻辑）

- 受影响契约 → 按 `story-to-contract` 的"重复执行语义"重跑收敛（幂等、零语义 diff）
- 受影响子需求/验收 → 按 `consensus-scan` 的闭环语义更新 Q-items（如验收标准变化产生新问题）
- 受影响测试场景 → 更新契约测试矩阵表，标"待复核"

## Phase 5：影响清单 + 待复核闭环

产出影响清单（`docs/spec/变更摘要` 追加或独立文件 `docs/spec/影响清单-<编号>.md`）：

```
# 影响清单（{规则编号} 变更）
| 受影响产物 | 路径/ticket | 处理方式 | 责任人 | 状态 |
|:-----------|:------------|:---------|:-------|:-----|
| DH-12 契约 | docs/api/jira-dh-12-api-contract.md | 已自动更新 | 张三 | 已确认 |
| DH-15 契约 | docs/api/jira-dh-15-api-contract.md | 待复核 | 张三 | 待复核 |
| QA 测试矩阵 T-023 | （契约内） | 待复核 | 王五 | 待复核 |
```

- 责任人确认后解除待复核（在载体/清单中记录确认）
- **复核完成前，受影响产物不得宣称交付完成**
- 变更相关 Q-items 状态同步更新（受影响规则对应的条目）

## 产出确认

汇报：变更摘要、影响清单（数量/类型/责任人）、已自动更新的、待复核的、以及需要人工拍板的争议项列表。
