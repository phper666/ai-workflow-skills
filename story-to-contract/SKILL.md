# 工作项转前后端接口契约

以项目管理工具的工作项为范围锚点，以仓库当前共识文档为业务事实源，以代码和数据库迁移为实现证据，生成可供前端开发、后端实现、联调和接口测试共同使用的契约。

## 固定边界

- 工作项只负责范围、文档导航和验收目标，不能覆盖共识文档。
- 标记为 `TBD`、开放问题或建议基线的内容不得擅自固化为契约。
- 默认只读 PM 工具，生成或更新本地文档。
- 共识扫描阶段负责发现模糊点，并将待确认项同步到团队约定的 Q-items 载体；本 Skill 消费当前共识、开放问题登记和决策结果，不重复创建同一待确认项。
- 没有未关闭 P0 待确认项且契约文档验证完成时，主动询问当前后端开发者是否按契约创建后端实现子任务；P1/P2 不阻止提示。
- 存在未关闭 P0 时默认不主动提示创建，先报告对应的待确认项或仓库开放问题。
- 用户明确要求创建子任务时，可以越过 P0 自动提示门禁；必须先展示 P0 风险和受阻范围，再执行独立确认。创建任务不代表 P0 已关闭，也不得把待确认内容固化为实现。
- 只有用户看到子任务预览并明确确认后，才调用 PM 工具写操作创建；创建时将经办人设置为当前已认证的用户。
- 创建子任务不修改父工作项状态，不自动创建成员账号，不分配给父工作项经办人或其他成员。
- 不替前端、测试或其他角色创建子任务；各角色使用自己的流程在父工作项下创建并认领任务。
- 仅在用户明确要求 `--sync-pm` 或明确要求回写 PM 工具时，预览评论内容并获得确认后调用 PM 工具写操作。
- 不执行 `git commit`、`git push`、分支操作或部署，除非用户单独明确要求并完成风险确认。

## 参数语义

- 工作项 URL 或 Key：例如 `https://team.atlassian.net/browse/DH-12`、`DH-12`（Jira）；`https://www.tapd.cn/12345678/prong/stories/view/1123456789001000001`（TAPD）。
- `--dry-run`：分析并预览契约，不写文件、不回写 PM 工具。
- `--ask-only`：只扫描模糊点和阻塞项，不生成契约。
- `--sync-pm`：契约完成后，预览并确认，再把文档路径、摘要和阻塞项写入工作项评论。
- `--create-task`：用户明确要求创建后端子任务。无论是否存在 P0，都先生成预览和风险说明并请求明确确认；不能跳过确认直接创建。

未提供 `--create-task` 时，只要没有未关闭 P0 且文档验证完成，也要在交付末尾主动询问是否创建后端子任务。用户拒绝或未明确确认时，不调用 PM 工具写操作。

## 重复执行语义

同一个工作项可以重复执行，本 Skill 必须表现为幂等的当前态收敛流程：

1. 使用固定输出路径定位已有契约，不创建 `-v2`、`-final`、日期副本或第二份同工作项契约。
2. 先读取已有契约，再重新读取工作项、评论、Q-items 待确认项、共识文档、决策记录、代码、测试、Flyway、OpenAPI 和相关模块契约；不得沿用上次执行缓存代替当前事实。
3. 计算当前来源相对已有契约的变化：待确认项关闭/新增/改优先级、接口新增/修改/删除、字段和枚举变化、错误语义变化、实现与契约冲突。
4. 已关闭待确认项必须核对可引用的决策或共识来源，再把结论合入对应 Schema、接口、状态、错误和测试场景；删除关联 `TBD` 和开放问题行。
5. 仍开放的问题保留当前优先级和影响，不因代码已经先行实现而自动视为已回答；代码不能覆盖更高优先级的共识。
6. 代码、Flyway 或 OpenAPI 新增了契约未记录的行为时，按事实优先级更新契约或报告冲突；破坏兼容的变化单独提示。
7. 只保留当前有效契约。更新变更记录的一行摘要，不累积旧审查过程、删除线或已关闭问题清单。
8. 若所有来源均未变化，再次执行不得产生语义或格式 diff。
9. 若父工作项已存在对应 `BE` 子任务，不创建重复任务；需要同步新契约路径、阻塞项或范围时，先预览 PM 工具更新内容并独立确认。

## Phase 1：定位工作项

1. 根据 URL 格式识别 PM 平台，加载对应适配器（[adapters/](adapters/)）。
   - `atlassian.net` → Jira
   - `tapd.cn` → TAPD
   - `linear.app` → Linear
   - `github.com` → GitHub Issues
   - `work_packages` 路径 / OpenProject 实例 → OpenProject（需 `OPENPROJECT_URL` + `OPENPROJECT_API_KEY` 环境变量）
2. 调用 `adapter.parseUrl(url)` 提取定位信息 → 获得 `ItemRef { workspaceId?, projectKey?, itemId, itemKey, itemType }`。
   - 只有 Key 时：从对话或项目配置获取平台上下文。
3. 调用 `adapter.readItem(ref)` 读取工作项详情 → 获得 `ItemDetail { key, url, title, description, status, type, assignee, parent, children, comments, labels }`。
4. 调用 `adapter.getCurrentUser()` 获取当前用户 → `{ id, name }`。不得用父工作项经办人代替当前用户。
5. 校验工作项类型。优先接受 Story；若是 Task/Epic/Bug，说明差异，但只要范围与验收足够明确仍可继续。
6. 记录完整的 `ItemRef` + 当前用户信息。

输出工作项摘要和文档引用清单，不修改 PM 工具。

## Phase 2：读取仓库治理与共识

先读取仓库根目录的 `AGENTS.md` 以及其要求的入口文档。若无 `AGENTS.md`，读取 README、文档索引和开发规范。

然后解析 Story 描述中的：

- 仓库相对路径、绝对路径和网页链接；
- 业务域编号、规则编号、场景编号、验收编号；
- 接口契约、开放问题、决策记录和非功能规范；
- 原型、附件或外部设计链接。

对每个引用执行：

1. 验证文件存在且引用有效。
2. 读取当前版本，不使用历史聊天或旧 RSD 覆盖当前共识。
3. 建立追踪表：`Story 范围 -> 共识规则 -> 验收标准 -> 开放问题`。
4. 同时记录待确认项的业务优先级和契约影响级别：
   - P0：自动提示创建子任务的阻塞项。
   - P1/P2：不阻止提示或创建，但必须写入任务依赖、限制和验收风险。
   - 未标优先级：自动提示门禁中按 P0 处理，直到共识扫描流程补齐优先级。
   - Blocker：会改变字段、状态机、鉴权、幂等、事务、数据隔离或外部契约。
   - Major：允许先搭框架，但不能宣告模块验收通过。
   - Minor：可采用仓库既有约定且不改变业务语义。

5. 若 Story 或共识文档引用了 Q-items 载体（如飞书多维表格、Jira q-item 子任务等），读取与当前工作项/模块相关的记录；以待确认项编号去重，不把不同载体中的同一问题重复计数。

若工作项只写了本地相对路径，而执行环境无法访问仓库，停止并要求仓库或文档链接；不得凭工作项摘要生成正式契约。

## Phase 3：提取用户操作与数据流

从 Story、共识和原型提取结构化清单：

```yaml
use_cases:
  - actor: 数据管理员
    action: 测试 Salesforce 连接
    preconditions: [已填写连接参数]
    success: 返回可诊断的成功结果并记录测试历史
    failures: [认证失败, 超时, 地址被安全策略拒绝]
    consensus_refs: [CON-R012, CON-AC001, CON-AC002]
```

同时记录：

- 页面需要的查询、创建、编辑、启停、触发和导出操作；
- 状态及合法转换；
- 字段来源、必填性、枚举、格式、敏感性；
- 分页、排序、筛选和时间语义；
- 鉴权、租户隔离、幂等和审计要求；
- 外部系统调用及失败恢复。

纯 UI 行为标记为 `frontend-only`，不得为其编造后端接口。

## Phase 4：扫描模糊点

按下列维度扫描并去重：

- 范围：本期做与不做是否明确；
- 状态：合法转换、触发条件、冲突行为是否明确；
- 字段：类型、必填、枚举、来源、默认值、敏感性是否明确；
- 接口：鉴权、分页、错误、幂等、异步查询是否明确；
- 数据：唯一性、删除、版本、事务、保留和隔离是否明确；
- 外部系统：认证、超时、重试、限流和部分失败是否明确；
- 验收：成功、失败、安全和兼容场景是否可观察。

格式：

```text
[BLOCKER][Q-012][后端/产品] RI+ 批量写入超时后无法判断是否成功，当前不能冻结重试契约。
```

处理规则：

- 已被共识、决策记录或代码明确回答：记录来源并自动关闭候选。
- Blocker：契约中标记 `TBD`，禁止编造；关联仓库开放问题或 Q-items 载体记录。是否自动提示创建子任务由 P0/P1/P2 决定，不由 Blocker/Major/Minor 决定。
- 新发现且尚未登记的问题：报告缺口并交回共识扫描流程写入 Q-items 载体；本 Skill 默认不直接新增记录，避免出现两套入口和重复问题。
- `--ask-only`：输出候选问题后结束。
- 用户要求回写问题时，只以父工作项评论形式提出；不创建子任务。PM 问题只陈述事实与缺口，不诱导选择技术方案。

## Phase 5：分析现有代码与契约

目标是生成增量契约，不重复定义已存在能力。

1. 使用 `rg` 定位模块、Controller、DTO、领域模型、外部适配器、Repository、migration 和已有 OpenAPI。
2. 先定位字段或业务对象的宿主模块，再反推接口；不要仅按页面按钮名称猜 Controller。
3. 对已有接口记录真实路径、方法、字段、校验、错误映射和调用方。
4. 对数据库行为读取 Flyway 或仓库实际 migration，不用 H2 或旧 schema 快照替代 PostgreSQL 证据。
5. 扫描其他模块契约，识别共享 Schema、可复用接口和跨模块冲突。
6. 分类：`UNCHANGED`、`NEW`、`MODIFIED`、`REMOVED`。删除或破坏兼容必须单独提示。
7. 已有契约时逐项对比接口路径、请求/响应字段、公共异常集、特有异常、状态、权限、事务、外部调用和测试场景，形成仅用于本次更新的差异清单。

任何“参照、复用、沿用现有模式”的结论必须附 `文件:行号` 证据；涉及入库、状态转换或权限时，至少核对代码与 migration/配置中的两层证据。

## Phase 6：生成契约

读取以下参考文件：

- [接口契约模板](references/api-contract-template.md)
- [契约生成规则](references/generation-rules.md)
- [契约审查规约](references/review-rubric.md)

优先使用仓库已有契约目录和命名。没有既有规则时使用：

```text
docs/api/{platform}-{item_id}-api-contract.md
```

文件名中的 item_id 转为小写。示例：
- Jira: `docs/api/jira-scrum-5-api-contract.md`
- TAPD: `docs/api/tapd-1123456789001000001-api-contract.md`

生成内容必须覆盖：

- Story、共识规则、开放问题和验收编号的追踪矩阵；
- 前端需要理解的接口、Schema、枚举、状态和错误；
- 后端必须实现的鉴权、事务、幂等、外部调用和持久化约束；
- 测试可直接执行的成功、参数、权限、冲突和依赖失败场景；
- 请求/响应示例和兼容性说明；
- 协调事项（跨模块/第三方，指定责任人与截止时间）；
- 数据库变更仅作为实现附录，不把 Entity/表结构直接暴露成外部响应模型。

若仓库以 OpenAPI 为正式接口源，应同步生成或更新对应 OpenAPI 文件；Markdown 用于解释追踪、规则和测试依据，不能与 OpenAPI 字段重复漂移。

已有文档时按“重复执行语义”做原路径增量更新：先把已关闭问题的决策合入正文，再清除对应 `TBD`、开放问题行和临时过程记录。不要累积删除线、历次审查日志或废弃方案。

## Phase 7：验证

按 `references/review-rubric.md` 执行最多两轮：

1. 第一轮发现问题后修正。
2. 第二轮验证；仍有 Blocker 时停止修改并报告，不继续自我循环。Blocker 不等同于 P0，也不自动禁止创建受阻子任务。

至少验证：

- 每个接口可追溯到 Story/共识/验收；
- 每个必填字段、业务规则和权限约束有失败场景；
- OpenAPI 与 Markdown 一致；
- Schema 不使用模糊 `Map<String,Object>` 或占位值；
- 状态码、错误码、分页、时间和幂等行为明确；
- 敏感字段不出现在响应、日志示例和审计差异中；
- 所有 `TBD` 都关联开放问题或工作项评论；
- Markdown 链接与引用路径有效；
- 执行 `git diff --check`。纯文档修改不要求运行 Maven；若同步修改可执行代码或 OpenAPI 生成逻辑，按仓库规范运行对应验证。

## 复核模式：FE/QA 契约复核（步骤 8）

用户以 FE 或 QA 视角要求复核契约时（"复核这个契约，我是 FE"），按 `references/review-feqa.md` 执行：

- FE 视角：联调可用性（字段覆盖、错误处理、示例、Mock/OpenAPI 一致、分页/时间语义）
- QA 视角：可测试性（成功+失败场景、边界值、验收编号绑定、可直接执行）
- 只查实现契约问题，**不重新猜测产品规则**；产品规则疑点转待确认闭环（consensus-scan），不在此解决
- 输出：通过（契约置已冻结）/ 退回（意见清单，BE 修改后重新复核）/ 阻断问题登记开放问题
- **通过后衔接**：契约冻结完成 → 下一步按 `tech-design` 判级——复杂/高风险需求（状态机、安全/权限/资金/数据、多模块、greenfield、外部系统集成）先产出 `docs/design/<id>-<module>-design.md` 技术方案并经评审，再进入实现；常规/简单需求直接进入实现

## Phase 8：交付与可选 PM 回写

输出：

- 契约文档路径；
- 新增、变更、复用接口数量；
- P0/P1/P2 待确认项及 Blocker/Major 契约影响；
- 子任务创建门禁状态；
- 实际执行的验证。

默认不修改 PM 工具。`--sync-pm` 或用户明确要求时：

1. 先展示拟写入的评论全文。
2. 获得确认后调用 `adapter.addComment(ref, body)`。
3. 评论只包含文档路径/链接、契约摘要、开放问题和验证状态。
4. 评论回写与子任务创建是两个独立确认，不得用一次确认代替另一次确认。

## Phase 9：提示或按明确要求创建后端实现子任务

满足以下条件时自动进入提示阶段：

- 工作项范围、共识规则和验收编号可追溯；
- 未关闭 P0 数量为 0；P1/P2 允许保留；
- Markdown/OpenAPI 已完成两轮内验证；
- 父工作项所在平台支持子任务（Jira Sub-task / TAPD 子需求 / Linear Sub-issue / GitHub task list）。

用户明确说“创建子任务”、传入 `--create-task` 或同义指令时，即使存在 P0 也进入本阶段。此时必须把任务标记为受阻，并在描述顶部列出未关闭 P0、受影响接口/字段和“不得实现未决部分”的限制。

根据实际契约为当前后端工作生成一个最小完整子任务：

- `后端：<模块能力>`：API、应用/领域逻辑、持久化、外部适配、安全和后端测试。

契约文档属于该后端子任务的输入和交付物，不再机械拆出独立“契约”子任务。子任务描述必须包含：

- 父工作项 Key 和契约文档路径；
- 范围与非目标；
- 负责接口或场景；
- 共识规则与验收编号；
- 完成标准和验证要求；
- 依赖关系、全部 P0/P1/P2 待确认项及对应契约影响。

执行顺序：

1. 先展示拟创建后端子任务的标题、类型、当前用户经办人、描述摘要、依赖和待确认项；存在 P0 时明确显示“任务可创建但当前受阻”。
2. 使用仓库要求的危险操作确认格式，要求用户明确回复 `y`。
3. 收到 `y` 后调用 `adapter.createItem(parentRef, { title, description, type, assigneeId })` 创建子任务。
   - Jira：创建 issuetype=Sub-task 的子任务。
   - TAPD：创建带 parent_id 的子需求。
   - Linear：创建带 parentId 的 Sub-issue。
   - GitHub：在父 Issue body 中添加 `- [ ]` task list 项。
4. 不修改父工作项状态，不把子任务分配给其他成员。
5. 创建后重新读取父工作项和子任务，核对创建结果。
6. 创建失败时报告失败原因，不用不同标题重复创建。
7. 创建前检查父工作项的现有子任务；已有同模块 `BE` 子任务时停止创建并报告其 Key，除非用户明确要求在预览后更新现有任务。

自动流程中若存在未关闭 P0，输出“当前存在 P0，默认不主动创建后端子任务”，列出对应待确认项/开放问题。若用户随后明确要求创建，则按上述受阻任务流程预览并确认；P1/P2 不阻止提示。

## 交付核验模式（步骤 10）

用户报告开发完成要求核验时（“DH-12 开发完了，核验” / “提测，按契约核验”）：

核验分三层，同一趟跑完，顺序固定：

### ① 设计核验（对照技术方案）

仅当存在技术方案文档（`docs/design/<id>-<module>-design.md`，见 tech-design skill）时执行：

1. 对照技术方案逐项核验：架构决策、模块划分、关键机制落地情况——用代码证据，不凭印象
2. 输出偏离清单：实现与设计方案的每处差异 + 处理结论
   - 有意的偏离 → 更新技术方案文档 + 记录理由（方案跟随实现合法，必须显式）
   - 无意的偏离 → 修实现
3. 偏离处理结论写入技术方案文档“核验记录”章节

无技术方案文档的常规/简单需求 → 跳过设计核验，不强制补方案。

### ② 契约核验（对照契约）

1. 对照契约逐项核验实现：接口路径/字段/错误码/权限/幂等/状态机——用代码 + migration 两层证据，不凭印象
2. 输出偏差清单：实现与契约的每处差异 + 处理结论（修实现 / 走变更流程更新契约——**不能口头绕过文档**）
3. QA 侧：按契约“联调与测试场景”表执行验证，核心路径 + 错误路径 + 兼容，输出 PASS/FAIL + 证据
4. 核验通过后填写契约“完成记录”章节（交付/验证/构建/发布结果，要有证据）

### ③ PRD/业务核验（对照 PRD + 原型）

产品需求产物 = **PRD + 原型**（UI 类需求），两者构成需求回溯链起点。复杂任务应在需求探索阶段产出（tech-design 前置）：

- **复杂任务：PRD/原型缺失 = 阻断**——需求不可回溯，补产后再核验（不静默放行）
- **常规任务/存量需求**：缺失时标记“无 PRD/原型”，不阻塞但记录

核对清单：

1. **产物存在性**：PRD 存在？原型存在（UI 类）？
2. **判级匹配**：实际实现复杂度 vs tech-design 判级声明——防“该走复杂的走了常规”（实现是否跳过了本应执行的实现纪律）
3. **实现纪律执行核对（执行钩子）**：implement-discipline 各环节证据——测试覆盖核心路径（单测 + 该有的集成测试）？lint 记录？review 无新增问题？semgrep 0 或已记录降级？（此核对归实现纪律一处管，不重复建 TDD 合规体系）
4. **需求落实核对**：PRD 需求逐项落实 + 原型交互/流程落实（有 PRD/原型时）

输出：核对清单结果 + 缺口 → 补做或记录偏差。
5. 有复用价值的实现决策/踩坑写入“决策与踩坑”章节（可复用才写，不写过程叙述），并同步候选 lessons（见 lesson-deposit skill 三硬标准）

偏差处理结论必须是可追踪的：记录在契约变更记录中，涉及共识语义的偏差先升级共识（consensus-scan 闭环）再改契约。

**核验通过 = 设计核验无偏离（或已显式记录）+ 契约核验零偏差**，之后才可宣称交付完成、进入沉淀。

## 范围收缩门禁

当用户要求“不做、去掉、跳过、不校验、不鉴权、不审计、不隔离”等范围收缩时，先回显：

- 受影响的接口、Schema、错误场景和测试；
- 兼容性、数据安全、审计和合规风险；
- 仓库中已有代码、migration 或配置的反向证据；
- 后续补齐路径。

涉及权限、凭据、租户隔离、PII、幂等或事务时，必须等待用户明确确认后才能修改契约。
