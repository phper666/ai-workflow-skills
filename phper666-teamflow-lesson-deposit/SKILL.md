# 经验沉淀（lessons）

沉淀是事后经验（踩坑/教训/可复用模式），与事前决策（phper666-teamflow-tech-design 技术方案）是两类产物，不混。**决策让人拍板，沉淀让时间验证。**

## 写之前：三硬标准（全中才写）

1. **可复用**：换模块/换项目还能用？——决策理由、可复用模式、坑的绕法。一次性的不写
2. **非显而易见**：读文档/git log 查不到、不翻代码不知道的隐性知识。明显的没人需要记录
3. **有代价**：踩过坑、花过时间换来的。免费知识不沉淀

三条全中 → 写；缺任一 → 不写（留在 git history 即可）。

## 写之后：自证机制（不绑人审）

- **引用计数**：写时登记引用位置（`来源` 字段）
- **复用验证**：后续同类工作真用到 → 引用 +1
- **90 天无新引用** → 标 `archived`（降级不删，从索引隐藏）
- 价值由"是否被再次使用"证明，不由审批证明；团队有 review 流程可顺带过滤（可选），没有则靠复用数据自愈

## 产出

`docs/lessons/<date>-<slug>.md`（slug 用主题词，如 `2026-08-15-overlay-atomic-swap.md`）

```markdown
# <决策/踩坑标题>

| 项 | 内容 |
|:---|:-----|
| 背景 | 什么场景下遇到 |
| 决策或坑 | 结论是什么 / 坑是什么 |
| 影响 | 不这样做会怎样 |
| 适用范围 | 哪些模块/场景适用，哪些不适用 |
| 来源 | 共识/契约版本 + 规则号 + 代码/提交引用 |
| 引用 | 首次引用位置；后续复用 +1 |
```

## 触发时机

- 交付核验通过后：实现决策/踩坑的候选 lessons（phper666-teamflow-story-to-contract 交付核验"决策与踩坑"章节同步候选）
- 踩坑当时：用户说"这个坑记一下"、"记个教训"
- 复盘时：phper666-teamflow-consensus-scan 复盘升级顺带审 lessons 质量（重复/过时的归档）

## 纪律

- 只写可复用知识：不写 UI 调整、CRUD、配置变更、纯过程叙述
- 不写流水账；单篇聚焦一个可复用点
- lessons 是索引不是日志——过程叙述留在 git history
- 旧的 >90 天无引用条目 → archived 标注，不删除
