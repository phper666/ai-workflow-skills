# 快速上手 — 10 分钟跑通第一个需求

> 人读 + AI 可执行双形态：你可以自己读着做；也可以对 AI 说
> **「带我跑一遍快速上手」**——AI 会按本文档逐步引导，每步等你确认再继续。

## 它解决什么

装好 skills 之后、跑完第一个需求之前的引桥：只走最小闭环（4 步），
高级概念（判级/评审机制/worktree 模式/变更传播/沉淀）在文末链接，不在这里展开。


**你说**："给这个项目接入研发工作流"

**AI 会**：建 docs/ 目录结构 → 检测载体（飞书/Jira/...）→ 生成团队配置.md → 写 AGENTS.md 导航段

**产出**：docs/spec/团队配置.md + 规则索引.md + AGENTS.md 导航段

**团队配置是什么**（接入已生成，现在全部用默认就能跑）：

| 配置项 | 管什么 | 默认 |

## 第 2 步：建立共识（2 分钟）

**你说**："给 XX 模块建立 XX 需求的共识文档"

**AI 会**：从 PRD/你的讨论提取整理 → 生成 15 节骨架的共识文档 → 发布基线（版本化）

**产出**：docs/spec/共识-<模块>-<需求标识>.md

**发生了什么**：共识 = 业务的唯一事实源。之后契约、实现、交付核验全部以它为准——
需求理解有分歧时，答案在这份文档里找（不是在聊天记录里翻）。

**真实产出片段**（共识文档头部，摘自真实项目）：

> - **本版本变更**：v1.3 已发布——**pnpm peer deps 需显式 fixup（cicd 首次实测发现，2026-08-26）**：pnpm 装 dsh 后 `dsh-app-boot` 的 9 个 peer（cordis-plugin-group 等）不链接到顶层 node_modules → dsh 启动 `ERR_MODULE_NOT_FOUND`。与 yarn 同因（peer 不自动装）但机制不同：**pnpm `auto-install-peers=true` 对传递依赖的 peer 不生效**（dsh-app-boot 是 dsh 的依赖非顶层），须装后显式 `pnpm add <peer>@<versionRange>`（peer fixup）。CON-R-pkgmgr-002/003 补充 peer fixup 语义。

> - **状态说明**：v1.2 已发布（去 yarn，两包管理器 npm/pnpm）；无未决项、无扫描待确认项。

## 第 3 步：生成契约（2 分钟）

**你说**："为这个需求生成接口契约"（配合工作项或直接说）

**AI 会**：读共识 + 现有代码 → 生成叙事契约 + OpenAPI 双文件 → 交付核验时对照

**产出**：docs/api/<契约>.md + <契约>-openapi.yaml

**发生了什么**：契约 = 前后端共享的接口约定（字段/状态/错误/测试场景）——
前端不用问后端"这个字段什么意思"，看契约；接口变更走契约，不靠口头。

**真实产出片段**（契约头部，摘自真实项目）：

## 第 4 步：实现 + 交付核验（2 分钟）

**你说**："按契约开始实现" → 实现完成后 → "开发完了，核验"

**AI 会**：实现纪律（测试/lint/必要 TDD）→ 交付核验三层（设计/契约/PRD 对照）→ 通过后 ticket 移 Done

**产出**：代码 + 测试 + docs/records/<需求>-record.md（实现记录与核验记录）

**发生了什么**：核验 = 「做完」不等于「做对」的兜底——实现对照设计、契约、PRD 三层，
有偏差要么修要么显式登记，不允许口头绕过。

## 常见第一问

| 问题 | 一句话答案 | 详见 |
|:-----|:-----------|:-----|
| 为什么要有共识？ | 业务事实唯一源，分歧时以它为准 | 角色使用手册 |
| Q-items 和 ticket 什么关系？ | Q-item=待确认的问题（要回答），ticket=要实现的任务 | 共识扫描 skill |
| 我一个人用要走全流程吗？ | 常规需求可轻量（小任务 git commit 即可），复杂需求才全流程 | 全局 AGENTS 需求分类路由 |
| 载体（飞书/Jira）必须配吗？ | 有 PM 平台就配（同一平台管理），没有可跳过先用文档 | 配置说明 |
| 出问题/不符合预期找谁？ | Q-item 登记待确认，结论回写共识 | 共识扫描 skill |
