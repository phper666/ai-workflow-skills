# 团队 AI 研发工作流 — 角色使用手册

> 配套：`ai-team-workflow.html`（流程可视化）· `团队AI研发工作流-落地启动文档.md`（落地手册）· `团队AI研发工作流-Skill规格文档.md`（skill 规格）
> 定位：每个角色的"怎么用"手册。核心承诺：**每角色只需记住 2-3 个 skill 的触发句，其余全是 agent 干活。**

---

## 0. 一句话总览

| 角色 | 碰的 Skill | 触发时机 |
|:-----|:-----------|:---------|
| 初始化者 | `phper666-teamflow-workflow-setup` | 项目开始前，用一次 |
| 产品经理 | `phper666-teamflow-consensus-doc`（4 模式）+ `phper666-teamflow-consensus-scan`（闭环） | 每模块 + 每基线 + 扫描后 |
| 后端 | `phper666-teamflow-consensus-scan`（扫描）+ `phper666-teamflow-story-to-contract`（4 模式）+ 实现三件套（tech-design / implement-discipline / lesson-deposit） | 每基线 + 每个子需求 + 实现阶段 |
| 前端 | `phper666-teamflow-consensus-scan`（FE 视角）+ `phper666-teamflow-story-to-contract`（复核） | 每基线 + 每契约 |
| QA | `phper666-teamflow-consensus-scan`（QA 视角）+ `phper666-teamflow-story-to-contract`（复核/核验） | 每基线 + 每契约 + 交付前 |
| AI/责任人 | `phper666-teamflow-change-propagation` | 共识规则变更时 |

**流程链（9 步）**：共识 → 扫描 → 待确认闭环 → 契约 → 判级/技术方案 → 实现纪律 → 交付核验 → 变更传播 → 沉淀

## 1. 初始化者（技术负责人 / 接入人）

**用一次，用完不再碰。**

> "给这个项目接入研发工作流"

agent 做：检测 PM 平台（Jira/飞书/TAPD）→ 落地 3 份模板（共识 14 节 / 契约 12+ 节 / 变更摘要）→ 建规则索引 `CON-R001` 起 → 初始化 Q-items 载体（默认飞书多维表格，可配 Jira）→ **角色账号登记**（张三=BE、李四=FE…，让问题自动挂载到人）→ 写 AGENTS.md 导航。

**存量项目**："接入工作流，我们已有存量文档" → 存量标"未纳入"，从下一个新需求开始走；已有规则从可识别处开始登记编号。

**产出**：项目"可开工"。团队没人需要学命令。

## 2. 产品经理

**Skill**：`phper666-teamflow-consensus-doc`（建/发/评/拆）+ `phper666-teamflow-consensus-scan`（闭环）

**你的一天**：

### 2.1 建共识文档（从 PRD/原型提取，不重写）
> "建立订单模块共识，PRD 在 docs/prd/订单.md，原型链接是这个"

agent：读 PRD+原型 → 按 14 节提取（流程/状态机/权限/字段/规则）→ 出草稿 → 你逐节确认 → 建规则编号（`CON-R012：订单取消后库存自动回补`）→ PRD 里的"待定/稍后"自动进未决项登记。

**纪律**：你的 PRD 写得越结构化，共识越准；PRD 有洞，共识显式标洞，不帮你补。

### 2.2 发布基线
> "发布共识基线 v1.0"

agent：升版本+时间 → 关联原型/Epic/来源链接 → 生成扫描通知（范围+截止时间）→ 通知 BE/FE/QA。

### 2.3 评审就绪检查
> "订单模块评审前检查"

agent 跑 Gate A checklist（结构完整？规则可唯一引用？P0 清零？）→ 输出"可以开评审 / 还差 X 项"。

评审会后：
> "把评审结论回写"

agent：结论进正文 → 升版本 → 出变更摘要。

### 2.4 处理待确认项（你的闭环义务）
> "处理待确认项"

agent 列出所有 Q-items（飞书表/Jira）→ 你逐条回答 → agent 校验三连：**已回答 → 已回写共识文档 → 发起人复核**，缺一不关。

### 2.5 拆解子需求
> "拆解订单模块子需求"

agent：按模块切子需求 → 每个绑定共识版本+规则编号+验收标准+不做事项 → 建 PM 侧需求。**不替你建 BE/FE/QA 的任务**（各自角色自己建）。

## 3. 后端

**Skill**：`phper666-teamflow-consensus-scan`（扫描）+ `phper666-teamflow-story-to-contract`（生成/澄清/核验/沉淀）+ 实现三件套：`phper666-teamflow-tech-design`（判级/方案）、`phper666-teamflow-implement-discipline`（实现纪律）、`phper666-teamflow-lesson-deposit`（经验沉淀）

**你的一天**：

### 3.1 扫描共识（BE 视角）
> "扫描订单模块共识，我是 BE"

agent：查状态转换合法性 / 数据唯一性 / 权限 / 第三方重试幂等 / 一致性 → 输出问题：
```
[BLOCKER][Q-007][后端] 订单取消并发下库存回补可能重复扣减，幂等未定义。
```

### 3.2 生成契约（核心模式）
> "为 DH-12（订单取消）生成契约"

agent：读共识 → `rg` 定位代码（Controller/DTO/migration）→ 分类 UNCHANGED/NEW/MODIFIED → 产出契约**双文件**（`docs/api/jira-dh-12-api-contract.md` 叙事 + OpenAPI yaml，字段以 yaml 为唯一权威）→ 契约状态只允许**三态（草案/待评审/已冻结）**，受阻信息写开放问题表 → 未决问题标 `TBD(Q-007)` 不编造 → 自检两轮。

> 改需求时："更新这个契约" → 幂等收敛，不产生 -v2 副本。

### 3.3 澄清闭环（Q-007 怎么处理？）
agent 定性三分：
- **技术问题** → 你自决：给依据+方案+约束，更新契约
- **产品问题** → 自动升级 PM（先改共识再改契约）
- **跨模块** → 记协调事项 + 责任人 + 截止时间

### 3.4 判级与技术方案（契约冻结后先判级）
> "DH-12 判级"

agent 按 `phper666-teamflow-tech-design` 判级（复杂 / 常规 / 安全敏感），结论 + 一句理由写入实现记录。**实现前置 Gate（契约冻结 → 实现之间，强制，缺一项不得开始实现）**：
- **复杂 / 高风险** → 必产 `docs/design/dh-12-order-cancel-design.md` 并评审通过 → 方案状态 **draft → frozen**（评审记录留痕）；无方案文档或未冻结 = 不得进实现
- **工程基线三问** → git / 脚手架 / 测试框架逐项核验，缺失先搭（属判级环节，不算实现步骤）
- **实现偏离方案** → 显式更新方案文档；重大偏离 → 方案回 draft 重审

### 3.5 实现纪律（分级执行）
> "按实现纪律开发 DH-12"

agent 按 `phper666-teamflow-implement-discipline` 分级执行，顺序不可跳：
- **复杂** → TDD 写核心路径 → lint + type-check → Code Review → Semgrep
- **常规** → lint 单次 + 工程基线三问复核
- **安全敏感** → 强制安全扫描，工具缺失**不得降级**；其余工具缺失可降级并在记录中说明

结果留痕 `docs/records/dh-12-record.md`（实现记录 + 核验记录两节）。

### 3.6 实现决策（AI 给方案，你拍板）
> "取消接口怎么设计？"

agent 给 2-3 个方案 → 你选 → agent 记录选择+理由 → 归类：
- 纯技术 → 写契约"BE 自决事项"
- 影响产品语义（字段/状态机/权限）→ **自动升级 PM**，不得悄悄改
- 可复用 → 写"决策与踩坑"

### 3.7 交付核验
> "DH-12 开发完了，核验"

agent：对照契约 diff 实现（字段/错误码/权限/幂等）→ 输出"3 项偏差，2 修 1 走变更流程"。**回查判级匹配**：实现复杂度与判级结论不符、或判级缺失 → 核验不通过。

### 3.8 完成沉淀
> "更新 DH-12 完成记录"

agent：写完成记录（交付/验证/构建/发布/测试结果，要有证据）+ 决策与踩坑章节；可复用的坑走 `phper666-teamflow-lesson-deposit` **三硬标准过滤** → `docs/lessons/<date>-<slug>.md`（90 天无引用归档）。

## 4. 前端

**Skill**：`phper666-teamflow-consensus-scan`（FE 视角扫描）+ `phper666-teamflow-story-to-contract`（复核模式）

**你几乎不产生文档，只消费和挑刺。**

### 4.1 扫描（FE 视角）
> "扫描订单模块共识，我是 FE"

agent：查页面/字段/交互/空态/跨端差异 → 输出：
```
[BLOCKER][Q-010][前端] 取消弹窗在移动端无二次确认，但 Web 端有，跨端差异未定义。
```

### 4.2 复核契约（你的把关点）
> "复核 DH-12 契约，我是 FE"

agent：字段覆盖交互所需？错误码够区分 4xx/业务错？示例自洽？Mock/OpenAPI 与文档一致？→ 通过 / 退回+意见清单。**CONS-02 硬检查：md 接口清单与 yaml paths 双向一致，不一致直接打回**；契约状态只允许三态（草案/待评审/已冻结）。

**你的收益**：契约**已冻结**后 → "开工" → 按 Mock/OpenAPI 并行开发，不等后端。联调期不靠猜。冻结后再改 → 走变更流程，不静默改契约。

## 5. QA

**Skill**：`phper666-teamflow-consensus-scan`（QA 视角扫描）+ `phper666-teamflow-story-to-contract`（复核/核验模式）

### 5.1 扫描（QA 视角）
> "扫描订单模块共识，我是 QA"

agent：查验收口径可观察？边界/异常路径有定义？可测试性？→ 输出：
```
[MAJOR][Q-011][测试] 取消订单的验收标准缺少"退款失败"场景。
```

### 5.2 生成测试矩阵
> "按 DH-12 契约生成接口测试矩阵"

agent：从契约"联调与测试场景"表展开（成功/参数/权限/冲突/依赖失败 + 边界值）→ 每条用例标验收编号（测漏了有据可查）。**前提：契约已冻结（三态锁定）且通过 CONS-02 双向一致检查，未冻结先打回**。

### 5.3 交付核验
> "DH-12 提测，按契约核验"

agent：按契约执行验证（核心路径+错误路径+兼容）→ PASS / 偏差清单。

## 6. 全员 — 变更传播

**触发**：共识规则变更时，任何人对 agent 说：
> "R012 改了，传播一下"

agent：定点读变更摘要（grep/ctx_search 按规则号定位 `变更摘要-<模块>.md`，禁全文加载）→ 沿 R012 找引用（子需求/契约/测试）→ **分级处理**：

| 变更类型 | 处理 |
|:---------|:-----|
| 纯语义跟随、无争议 | AI 直接自动更新受影响契约 |
| 破坏兼容 / 涉及权限·数据·资金 / 需取舍 | 等对应责任人确认（只有被引用模块的人介入，非全员） |

→ 出影响清单：
```
影响清单（R012 变更）：
├─ DH-12 契约 → 已自动更新（库存回补：即时→延迟 24h）
├─ DH-15 契约 → 待复核（依赖失败场景引用 R012）
└─ QA 测试矩阵 T-023 → 待复核（回补时机断言需改）
复核完成前，DH-15 不得宣称交付。
```
→ 各责任人确认 → 解除待复核。

## 7. 灵活调配（小团队怎么跑）

**原则：角色是视角，不是人头。视角必须全覆盖，执行人可以少于角色数。**

| 团队配置 | 扫描怎么跑 | 契约复核怎么跑 |
|:---------|:-----------|:---------------|
| 1 产品 + 1 开发 + 1 测试 | 开发跑 BE+FE，测试跑 QA，产品管闭环 | 开发自审 FE 视角，测试审 QA 视角 |
| 1 产品 + 1 开发 | 开发跑 BE+FE+QA 三角色 | 开发自己带两顶帽子复核 |
| 1 人全干 | 默认单人模式（agent 自动三角色切换） | 全部自己审 |

**规则**：`--role=BE|FE|QA` 参数切视角；一个人跑多个视角时，**每次只带一顶帽子**（避免视角混在一起漏检）。

**实现阶段简化**：小团队把判级/实现纪律/沉淀合并跑——判级一句话记录、TDD 只覆盖核心路径、沉淀只写真踩坑（90 天无引用自动归档，不用维护）。

## 8. 载体与问题流（FAQ）

**Q1：共识从哪来？** 从 PRD/原型提取整理，不重写。PRD 是创作态，共识是事实源（结构化+编号，供所有角色和 AI 引用）。

**Q2：扫描发现问题会生成问题让 PM 确认吗？载体？** 会。写入 Q-items 载体（**默认飞书多维表格，可配 Jira q-item 子任务**，setup 时按环境检测），标"待 PM 确认"，绑定共识版本+章节+规则编号。

**Q3：PM 有问题要 BE/FE/QA 确认呢？** 会，同一套载体。Q-items 双向：谁有问题谁建，标给谁谁处理（字段：待确认角色）。

**Q4：待确认项解决后谁更新共识？** PM（skill 强制：回答→回写→复核三连，回写位置必填，不做完不关闭）。回写后升版本+变更摘要。

**Q5：共识更新后，已有契约怎么更新？** 不实时推送，按需收敛：主动（"传播一下"跑 phper666-teamflow-change-propagation）或被动（下次更新契约时 skill 重读共识自动合入差异）。

**Q6：需求/共识改了，契约全部直接改？** 不。先影响分析再分级：纯语义跟随 AI 直接改；破坏兼容/权限/资金/数据等争议项等责任人确认。只有被引用模块的人介入。

**Q7：决策与踩坑谁做？** 每角色做自己的：BE→契约"决策与踩坑"章节；FE/QA/PM→`docs/lessons/` 目录自己的文件；重复问题→复盘升级为扫描规则。纪律：可复用才写，不污染当前规格。

**Q8：AI 给方案 BE 拍板，决策怎么走？** 三层归类：纯技术→BE 自决（写自决事项）；影响产品语义→自动升级 PM（先改共识再改契约）；可复用→决策与踩坑。AI 永不替你拍板，但你的每个拍板都留痕可追踪。

## 8.1 补充问答（第二轮）

**Q1：PRD/原型写得不好，AI 会帮忙补足闭环吗？**
AI 会"追问补足"，不会"编造补足"：提取时自动检测洞（流程无状态机/字段无必填/权限未定义）→ 显式列出；建共识时逐项追问；未决项自动登记、下次扫描自动变 Q-items 提醒 PM。PRD 越烂，未决项越多——洞被显式暴露而非掩盖。闭环最后一环永远是 PM 回答。

**Q2：环境检测是什么？本地/服务器部署有影响吗？**
检测的是"当前会话能调什么工具"（Jira MCP / 飞书 MCP 可用性、凭据有效性），与部署位置无关。本地跑：检测本机凭据；AI 跑服务器：凭据配在那台机器，检测结果一样。载体选团队都能访问的（飞书多维表格天然适合）。

**Q3：待确认角色自动识别？能自动挂到具体人吗？**
三件事：① 自动识别——agent 按问题内容推断（库存幂等→BE，移动端空态→FE）；② 可修正——识别不准时创建时指定"待确认：FE"；③ 自动挂载到人——setup 做"角色账号登记"后，Q-items 自动 assignee=对应账号（Jira 经办人/飞书负责人字段），闭环精准推送。强烈建议登记。

**Q4：必须用 --role 全部跑一遍吗？**
不是。默认单人跑=agent 自动三角色切换，零参数。--role 是可选：团队分工各自跑单视角（需 merge 收口）或只想省时间看单视角。唯一纪律：**视角必须全覆盖**。

**Q5（原 Q6）：模块负责人=ticket 经办人？ticket 谁拆？**
是——影响清单"待复核"责任人=ticket 经办人；没 owner 的影响项标"无负责人"由 PM 指派。ticket 两级拆：**PM 拆子需求**（绑定共识版本+规则编号+验收标准），**各角色拆自己的任务**（BE 用 phper666-teamflow-story-to-contract 建，FE/QA 各自建）。不替别人建任务。

**Q6（原 Q7）：经验判断错误写错踩坑会怎样？**
影响限制在参考层，进不了执行层：决策与踩坑不是门禁不阻断流程；执行依据永远是共识+契约不是经验；有版本和变更记录可修正；错误经验升级成扫描规则会产生假阳性（误报）被团队发现撤下——假阳性是自纠机制。建议 lessons 文件加状态标记（新/已验证/已废弃）。

**Q7（原 Q8）：每个角色都是 AI 给方案、角色拍板？**
是，全流程统一：PM 拍业务事实、BE 拍技术决策、FE 拍前端决策、QA 拍用例覆盖、变更传播拍复核确认。**越界自动升级**——BE 拍板影响产品语义（字段/状态机/权限）自动升级 PM。AI 永不替你拍板，每个拍板都留痕可追踪。

## 8.2 补充问答（第三轮）

**Q1：能直接指定载体吗？中途换麻烦吗？**
能——setup 时直接说"用飞书多维表格"/"用 Jira q-item"，指定优先于自动检测。中途换：共识/契约文档零影响（在 git/wiki）；只有 Q-items 是状态数据，需迁移（早期几乎免费，积累多了要迁移脚本）。适配器层隔离，流程逻辑不用动。建议一开始定死。

**Q2：中途加入的人怎么登记？**
登记是增量维护不是一次性：映射表在 `docs/spec/团队配置.md`，说"登记新成员：孙七=QA"追加一行；换人/换角色同样更新+旧 Q-items 重新指派；agent 发现"待确认角色无账号"会主动提示登记。不用重跑 setup。

**Q3：四个角色的活都要切换角色跑一遍吗？setup 谁都能执行？**
不需要四角色全跑：扫描=BE+FE+QA 三视角（PM 不扫，PM 是回答闭环的人）、契约复核=FE+QA 两视角，默认单人模式自动全覆盖，--role 只用于分工/单视角。setup 技术上谁都能跑，推荐初始化者/技术负责人做（拍板平台、配载体、写导航）；一个项目一次，重跑幂等无害。

**Q4：做完需求就 AI 扫描一遍沉淀经验？**
不是。沉淀四层不同触发：完成记录=每需求必做（轻量证据）；决策与踩坑=过程中拍板时随手留痕；lessons=踩坑时随时写；复盘升级扫描规则=同一坑第二次出现或迭代末才做（节流阀）。沉淀是"有料才写"，不是"每需求必扫"。
