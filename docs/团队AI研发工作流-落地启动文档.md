# 团队 AI 研发工作流 — 落地启动文档

> 配套可视化：`ai-team-workflow.html`（流程总览）
> 配套执行器：`phper666-teamflow-story-to-contract` skill（契约生成/更新自动化）
> 定位：新团队从 0 推行本工作流的启动手册 — 基础设施、推行节奏、分角色沟通、工具合规评估

---

## 0. 流程一页图

**原则**：一份业务事实源，两级确认闭环（PM / BE），三道门禁（共识 A → 需求 B → 契约 C）+ 实现前置 Gate，一套自动变更传播。

| # | 步骤 | 负责人 | 门禁 |
|:--|:-----|:-------|:-----|
| 1 | PM 建立项目共识文档（规则编号 CON-Rxxx） | PM | — |
| 2 | 发布共识基线版本（绑定原型/Epic，通知扫描） | PM·文档仓库 | Gate A 前 |
| 3 | BE/FE/QA 分角色扫描共识（AI 查重聚类） | BE·FE·QA | Gate A：共识就绪 |
| 4 | 创建并闭环 PM 待确认项（回答→回写→复核） | PM | Gate A：阻断项清零 |
| 5 | 正式需求评审（验证成形共识，结论回写） | 全员 | Gate A 通过 |
| 6 | 拆分模块子需求与角色子任务（绑定共识版本+规则号） | PM·各角色 | Gate B：需求就绪 |
| 7 | BE 生成前后端契约文档（md + OpenAPI yaml 单一事实源、状态三态、CONS-02 一致性硬检查） | BE | Gate C：契约就绪 |
| 8 | FE 与 QA 复核契约可用性（联调+测试矩阵） | FE·QA | Gate C：契约就绪 |
| 9 | BE 待确认项分级闭环（技术自决/产品升级/协调事项） | BE | Gate C：阻断项清零 |
| 10 | 判级（tech-design：复杂/常规/安全敏感，结论+理由写入实现记录） | BE·技术负责人 | 契约冻结后 |
| 11 | **实现前置 Gate**：复杂/高风险必产 `docs/design/<id>-<module>-design.md` 且评审通过（方案冻结 draft→frozen）+ 工程基线三问（git/脚手架/测试框架） | BE·技术负责人 | 未冻结不得进实现 |
| 12 | 按实现纪律开发（分级：复杂 TDD→lint→Review→Semgrep；常规 lint+基线三问；安全敏感强制扫描），留痕 `docs/records/` | BE·FE·QA | 交付质量门禁 |
| 13 | 交付核验（对照验收标准：设计/契约/PRD 三层 + 判级匹配回查），留痕 `docs/records/<id>-record.md` | 全员 | 交付核验 |
| 14 | 上游变化自动标记下游失效（变更摘要→影响清单→待复核） | AI·各责任人 | 持续有效性门禁 |
| 15 | 完成记录与决策经验回流（证据+决策沉淀+规则升级） | 全员 | 闭环完成 |

## 1. 落地架构：四件基础设施

### 1.1 文档仓库（事实源的家）

```
docs/
├── spec/                  # 共识/规则索引/团队配置/变更摘要/影响清单
│   ├── <模块名>-共识文档.md
│   ├── 规则索引.md
│   └── 模板-共识文档.md    # 14 节骨架模板（见下）
├── api/                   # 契约文档（双文件：md + OpenAPI yaml 单一事实源）
│   ├── jira-<item>-api-contract.md
│   ├── jira-<item>-openapi.yaml
│   └── 模板-契约文档.md    # 12 节骨架（与 skill 模板一致）
├── design/                # 技术方案（复杂/高风险必产，draft→frozen）
│   └── <id>-<module>-design.md
├── prd/                   # 需求文档
├── prototype/             # 原型
├── records/               # 实现/核验记录 <id>-record.md
└── lessons/               # 经验沉淀
```

**要求**：
- 固定路径 + 固定命名，禁止 `-v2`/`-final`/日期副本（幂等更新前提）
- 模板先行：新人照着填空，不靠理解写散文
- 共识文档 14 节：元信息 / 结构总览 / 模块概述 / 流程与状态机 / 角色权限矩阵 / 字段定义 / 业务规则清单 / 枚举常量 / 第三方对接 / 未决项登记 / 页面交互规范 / 后端任务规范 / 端差异汇总 / 附录（规则索引+版本记录）
- 契约双文件：md 给人读 + OpenAPI yaml 单一事实源，状态三态，CONS-02 一致性硬检查

### 1.2 PM 工具配置（Jira / TAPD / 飞书任选，原则不变）

| 配置项 | 内容 |
|:-------|:-----|
| 待确认项载体 | q-item 子任务（或飞书多维表格），字段：共识版本、章节、规则编号、优先级 |
| 优先级体系 | P0（阻断）/ P1 / P2；契约影响：Blocker / Major / Minor |
| 强制字段 | 关闭待确认项必填"已回写位置" — 把回写做成表单约束，不靠自觉 |
| 子任务规则 | 各角色只建自己的子任务；经办人=当前操作者，非父需求经办人 |

### 1.3 规则编号规范

- `CON-R001` 起，全局唯一；规则集中登记在共识文档附录"规则索引"
- 第一天就建，成本≈0，是整个变更传播机制（步骤 11）的锚点

### 1.4 工具链

| 工具 | 对应步骤 | 状态 |
|:-----|:---------|:-----|
| `phper666-teamflow-story-to-contract` skill | 6/7/8/9/14 的核心 | 已有，合规评估见附录 A |
| `phper666-teamflow-tech-design` skill（判级/技术方案） | 10/11 | 已定义，随第一批复杂需求落地时启用 |
| TDD 测试框架 + lint/type-check（项目既有栈） | 12 | 工程基线三问核验 |
| `ocr`（open-code-review）代码审查 | 12 | 需配置 |
| Semgrep 安全扫描 | 12 | 有则跑，无则核验记录记风险项 |
| 扫描 prompt（三角色） | 3 | 需自建（可复用 skill Phase 4 维度） |
| 共识文档模板 | 1 | 需自建 |
| 变更传播流程 | 14 | 需定义（当前靠重跑 skill 收敛） |

## 2. 推行节奏：四阶段 rollout

**核心纪律：先跑通，再扩大。流程跟着真实需求走，不为流程造需求。**

| 阶段 | 内容 | 周期 | 完成标志 |
|:-----|:-----|:-----|:---------|
| **0 试点准备** | 选试点模块（正在做、有真实争议的需求）；建文档仓库+模板+规则编号；拉技术负责人当同盟 | 1 周 | 基础设施就绪 |
| **1 共识闭环** | 只推步骤 1-4：共识文档 + 扫描 + PM 待确认闭环 + Gate A。**不碰契约** | 2-3 周 | 试点模块跑完一个完整 Gate A |
| **2 契约闭环** | 加步骤 6-9：拆解 + 契约生成/复核 + BE 待确认闭环 + Gate B/C。**技术方案 + 实现纪律随第一批复杂需求落地时启用**（实现前置 Gate：判级 → 复杂/高风险出方案并冻结 → 工程基线三问） | 2-3 周 | 试点模块交付，FE/QA 全程未找 BE 口头问接口 |
| **3 传播沉淀** | 加步骤 14-15：变更传播 + 决策沉淀 | 持续 | 一次规则变更完整走完影响链路 |

**执行要点**：
1. 评审复用现有会议，不新增仪式（步骤 5 = 把已有评审内容前置收敛）
2. 每阶段用真实结果说话（"联调返工 X→Y"），不宣讲流程本身
3. 第二阶段起，让第一阶段跑通的人自己讲（同伴效应 > 权威效应）
4. 阶段 1 是生死线：共识闭环跑不通，后面全部别推

## 3. 分角色沟通指南

**原则：只讲每个角色关心的 WIIFM，用他的痛点讲，别展示全流程。**

| 角色 | 他的痛点 | 讲什么 | 承诺 |
|:-----|:---------|:-------|:-----|
| 产品经理 | 需求被反复挑战、评审吵不完、决策权 | 决策权不变，只加留痕；扫描替你提前发现漏洞，省得会上被三方围攻；待确认项有人负责闭环；反悔有版本可追 | 共识文档替代写需求文档的时间，非额外负担 |
| 后端 | 被打扰、需求说变就变、契约工作量 | 契约一次写清，FE/QA 不再联调期反复问；规则变更 AI 自动标记下游；技术决策写进沉淀，下次不重吵；技术自决权变大 | 非产品语义问题不用问 PM |
| 前端 | 接口没定没法开工、Mock 不靠谱 | 契约=并行开发许可证：按契约+Mock 开工，不等 BE；异常路径/错误码写全，联调不猜；契约先过 QA 复核 | 拿到的是被验证过的接口 |
| QA | 凭经验测、验收扯皮背锅 | 测试矩阵从契约直接生成；用例可追溯到规则编号，"测漏了"有据可查；验收口径与共识一致，不夹在中间传话 | 验收有共同依据 |
| 技术负责人 | 延期、返工、新人上手、知识流失 | 三道门禁卡漂移；变更传播杜绝"文档改了没人知道"；决策沉淀成团队资产；新人看共识+契约就能干活 | 他是你第一个同盟 |
| 老板 | ROI | 减少联调返工、变更可追踪、交付状态可查、不依赖个人 | — |

**反对意见预案**：

| 质疑 | 回应 |
|:-----|:-----|
| "写文档浪费时间" | 共识文档=替代你写需求文档；扫描是 AI 干活；省的是联调期 N 倍扯皮 |
| "敏捷要轻流程" | 流程只加在变化点（扫描/门禁/变更传播），日常开发零打扰 |
| "团队小不需要" | 越小越便宜：规则编号+模板一天建好；流程成本固定，团队大才贵 |
| "不用 Jira" | 载体可换 TAPD/飞书/Linear，只有规则编号是硬的 |
| "AI 不可靠" | AI 只做扫描查重、变更标记、知识沉淀；决策永远是人的 |

**个人入场三纪律**（新加入者视角）：
1. 先解决真实痛点再提流程 — 用最小子集解决问题，让结果说话
2. 先说服技术负责人，由他宣布流程，你做执行和工具
3. 自己先用 — 每个需求自己先写共识+契约，成为活样板

## 附录 A：phper666-teamflow-story-to-contract skill 合规评估

### A.1 结论

**skill 是流程中的"契约生成枢纽"执行器，不是流程本身。** 它完整实现了步骤 6-9 的核心机制，纪律（回写、TBD、P0 门禁、幂等收敛、证据要求）与流程同源。缺口集中在**上游创建侧**（共识文档、待确认项、跨角色扫描）和**人/组织侧**（评审、FE/QA 复核、变更推送），工具补不了，需团队流程+模板补齐。

### A.2 覆盖矩阵

| 步骤 | 覆盖 | 说明 | 缺口/补齐 |
|:-----|:----:|:-----|:---------|
| 1 共识文档 | ✗ | skill 是消费方（Phase 2 读取），明确"不能覆盖共识文档" | 需自建共识模板+创建流程 |
| 2 发布基线 | ✗ | 版本可追踪是 skill 的输入要求，但发布动作不在 | 团队流程：发布通知+绑定原型/Epic |
| 3 跨角色扫描 | ◐ | skill 有 Phase 4 扫描（维度完整：范围/状态/字段/接口/数据/外部系统/验收；格式 `[BLOCKER][Q-012][后端/产品]`） | 是"契约视角"扫描；三角色（BE/FE/QA）扫描+AI 查重聚类需自建，可复用其维度做三角色 prompt |
| 4 PM 待确认闭环 | ◐ | 消费侧完整：读 Q-items 载体、编号去重、已关闭核对决策来源再合入、不重复创建 | **不创建待确认项**（防两套入口）——创建入口需共识扫描流程补 |
| 5 评审 | ✗ | 不涉及 | 团队会议流程，复用现有评审会 |
| 6 拆解 | ◐ | 消费 Story 为范围锚点；Phase 9 创建 BE 子任务（预览→`y`→创建→复核；查重防重复；P0 门禁） | 子需求拆解（PM 侧）不在；skill 只生成 BE 子任务 |
| 7 契约生成 | ● | 完整：定位模块反推接口、UNCHANGED/NEW/MODIFIED/REMOVED 分类、Flyway 证据、TBD 纪律、固定路径幂等、追踪矩阵、12 节模板 | 无 |
| 8 契约复核 | ◐ | Phase 7 两轮自检 + review-rubric（10 条 Blocker：TRACE-01 追踪断裂 / OPEN-01 擅自关闭 / SEC-01 敏感泄露 / TASK-02 未确认写入等） | 是**单 agent 自检**，无 FE/QA 人工复核通道（联调视角+测试矩阵生成需人工或另建工具） |
| 9 BE 澄清 | ◐ | Blocker→TBD 关联开放问题、禁止编造、技术自决入契约、产品问题报告缺口交回上游 | 协调事项（跨模块责任人与截止时间）无独立机制 |
| 10 研发验证 | ✗ | 不涉及开发执行 | 团队开发流程；契约是执行依据的纪律需规范固化 |
| 11 变更传播 | ◐ | "重复执行语义"：重扫全部来源→算差异→增量收敛→零语义 diff；已关闭问题合入、未关闭保持 | 是**重跑式收敛**，非推送式：无"自动标记下游失效/创建影响任务/待复核"机制 |
| 12 沉淀 | ◐ | 契约有变更记录、自检记录；幂等收敛防文档膨胀 | 无"决策与踩坑"章节（模板 12 节不含）、无完成记录、无"重复问题升级为扫描规则" |

● 完整 ◐ 部分 ✗ 未覆盖

### A.3 缺口清单与补齐建议（按优先级）

| # | 缺口 | 影响 | 补齐方式 | 优先级 |
|:--|:-----|:-----|:---------|:------:|
| G1 | 共识文档模板与创建流程 | 步骤 1-2 无地基，全流程不可开始 | 建 `docs/spec/模板-共识文档.md`（14 节）；PM 按模板产出 | P0 |
| G2 | 待确认项创建入口 | 扫描发现问题无家可归（skill 明确不创建） | 建"共识扫描"入口：三角色扫描 prompt 复用 skill Phase 4 维度，发现→去重→写入 Q-items 载体 | P0 |
| G3 | 三角色扫描+AI 查重聚类 | 步骤 3 是 Gate A 前唯一防线 | 扫描 prompt 三份（BE/FE/QA 视角）+ 合并去重规则 | P0 |
| G4 | FE/QA 契约复核通道 | 步骤 8 目前只有 agent 自检，无消费方验证 | 复核 checklist（FE 联调可用性 + QA 测试矩阵），人工或独立 agent 执行 | P1 |
| G5 | 变更传播推送侧 | 步骤 11 只能"重跑收敛"，无主动失效标记 | 变更摘要模板 + 影响清单人工确认流程；后续可做引用图扫描脚本 | P1 |
| G6 | 契约模板缺"决策与踩坑/完成记录" | 步骤 12 知识沉淀断裂 | 模板加"决策与踩坑"章节（当前态纪律：沉淀不污染正文）；完成记录走工作项评论或独立记录 | P2 |

### A.4 skill 可复用资产

- **Phase 4 扫描维度**（范围/状态/字段/接口/数据/外部系统/验收）→ 直接做三角色扫描 prompt 的内核
- **优先级语义**：P0/P1/P2 + Blocker/Major/Minor → 全流程统一使用
- **TBD 纪律**：不编造、关联开放问题 → 全流程通用原则
- **重复执行语义**（幂等收敛、零 diff、固定路径）→ 所有文档更新统一遵守
- **review-rubric** 10 条 Blocker → 可升级为契约评审通用 checklist
