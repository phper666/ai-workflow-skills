# 共识文档生命周期（PM 侧）

管理模块共识文档的完整上游生命周期：**建立 → 发布基线 → 评审就绪 → 拆解子需求**。共识文档回答"业务应该是什么"，是唯一的业务事实源；下游所有产物（待确认项、子需求、契约、测试）都必须绑定它的版本和规则编号。

模板见 `references/模板-共识文档.md`（14 节骨架）；变更摘要模板在 `change-propagation/references/模板-变更摘要.md`（单一源）；多版本迭代/归档/分支约定见 `references/多版本策略.md`（正常迭代不归档，归档只在替换式大变更）。

## Phase 1：建立共识文档

**输入**：PRD、原型链接、已有共识（更新场景）、或仅口头业务描述。

1. 有 PRD/原型 → 读取并按 14 节骨架**提取整理**，不重写、不翻译成新叙事。PRD 是创作态，共识是事实源。
2. 纯口头 → 按 14 节逐节采集，每节确认后再进下一节。
3. 规则编号：为关键业务规则建立稳定编号（`CON-R001` 起，查 `docs/spec/规则索引.md` 现有编号避免冲突），每条规则记录：描述 / 来源 / 当前结论 / 变更状态。
4. 显式记录三样负面清单：**未决项**（PRD 里的"待定/稍后/未确认"字眼自动抓取登记）、**适用范围**（管哪些模块、不碰哪些）、**不做事项**（明确排除的需求）。没写这三样，别人会默认"没写=可以做"。
5. 检查自相矛盾：同一事实两处说法不一致时，停下来问用户，不自行取舍。

**TBD 纪律**：业务事实不确定就标未决项，**禁止编造**。你追问得越细，共识越准；PRD 有洞，共识就显式标洞，而不是帮你补。

## Phase 2：发布共识基线

用户确认文档内容后：

1. 升版本号 + 更新时间（版本不可歧义，如 v1.0；禁止 `final_v2_最终版` 式命名）
2. 关联原型、Jira Epic/父需求、来源材料链接
3. 生成扫描通知：范围 + 截止时间（内容：请 BE/FE/QA 在 X 前完成扫描）
4. 版本记录写进文档"附录与版本记录"，变更写"本版本变更"

**产出**：共识基线版本 + 扫描通知。后续所有问题必须绑定此版本。

## Phase 3：评审就绪检查（Gate A）

会前模式：用户说"评审前检查"时执行，输出"可以开评审 / 还差 X 项"：

- [ ] 结构完整，无明显自相矛盾
- [ ] 关键规则可被唯一引用（编号存在且索引登记）
- [ ] 未决项有登记（不要求清零，但必须显式）
- [ ] P0 待确认项已清零（查 Q-items 载体，见 consensus-scan）
- [ ] 文档版本可追踪
- [ ] 适用范围 / 不做事项已写

会后模式：用户说"评审结论回写"时执行：
1. 评审中确定的结论写入正文（不留在会议纪要）
2. 会议新发现的问题 → 走待确认闭环（consensus-scan），不例外
3. 升版本 + 输出结构化变更摘要（`change-propagation/references/模板-变更摘要.md`）

**评审的作用是验证已成形共识，不是第一次发现问题**。会前发现问题多，说明 Phase 1 或扫描没做完，先回去补，不硬开评审。

## Phase 4：拆解模块子需求

用户确认基线稳定后（Gate A 通过）：

1. 按模块拆子需求（Story/父需求级），每个子需求绑定：共识文档版本 + 引用规则编号 + 验收标准（可测试）+ 不做事项
2. 标注依赖：依赖模块 / 第三方 / 跨团队协调项
3. 范围检查：每个子需求可由一个交付周期覆盖
4. **只建 PM 侧的子需求**。BE/FE/QA 各自的交付任务由各角色自己建（BE 用 story-to-contract 的创建流程，FE/QA 用各自流程），不替别人建任务

**产出落地动作（Gate B 通过前必须完成，缺一不得进入契约阶段）**：

1. **子需求清单写入共识文档附录**（§14：编号/验收标准/规则绑定/依赖/顺序）
2. **PM 侧子需求 ticket 化**：写入 ticket 载体（类型按载体映射：Story / User story / 需求；字段：优先级、规则编号），记录 ticket id 到附录清单
3. **自查**：验收可测试 ✓ / 规则绑定 ✓ / 依赖标注 ✓ / 单交付周期可覆盖 ✓
4. **产出确认汇报**：清单表 + 载体位置 + Gate B 就绪

**产出**：模块子需求清单（绑定共识版本+规则编号，ticket 已落载体），满足 Gate B（需求就绪）。

## 纪律

- **落载体才算完成**：每个阶段"讨论定稿"不是产出——**落载体（文档/清单/ticket）才是**；未落载体不得进入下一阶段（Gate A/B/C 的落地动作是强制检查点，不存在"讨论完就跳下一步"）
- 共识文档只维护当前有效结论；历史结论进变更记录，不累积删除线
- 任何业务结论变化 = 升版本 + 变更摘要（这是 change-propagation 的输入）
- 未决项登记处与 Q-items 载体保持同步（共识里登记了 → 待确认闭环里要有对应条目）
- 文档结构以模板为准；确实不需要的章节写"本模块不涉及"，不删除章节（保结构稳定）
