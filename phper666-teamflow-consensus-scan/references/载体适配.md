# Q-items 载体适配

待确认项（Q-items）载体由 `docs/spec/团队配置.md` 指定。**原则：载体 = 团队现有 PM 平台（5 选 1），同平台管理工作项与待确认项，推广阻力最小；飞书多维表格是"无 PM 平台团队"的默认。**

skill 主体只写抽象字段，平台差异在本文件描述。五平台均支持；选择后尽量不变，更换只需迁移 Q-items 数据，流程逻辑不变。

## 通用字段（五平台一致）

| 字段 | 说明 |
|:-----|:-----|
| 编号 | Q-001 起，全局唯一，去重依据 |
| 问题 | 单条问题描述（含触发场景） |
| 优先级 | P0（阻断）/ P1 / P2 |
| 契约影响 | BLOCKER / MAJOR / MINOR |
| 待确认角色 | PM / BE / FE / QA |
| 创建人 | 发起视角或人名 |
| 共识版本 | 绑定基线版本 |
| 章节/规则编号 | 定位锚点（变更传播依赖） |
| 状态 | open / answered / closed |
| 回答 | 单义结论 + 适用范围 + 生效时间 |
| 回写位置 | 强制：共识文档章节/规则号 |
| 复核人 | 发起人 |

## 飞书多维表格

- 接口选择（按执行环境，**先检测再用**）：
  - **环境有飞书 MCP 工具**（`feishu_manage_bitable_record` 等）→ 用 MCP：`feishu_manage_bitable_record` action=search/create/update，filter 按编号/状态
  - **环境只有 lark-cli** → 加载 `lark-base` skill，用 `lark-cli base` 等价命令操作（建表/写记录/更新/查询）
  - 两套接口语义等价：表名"待确认项"，字段见"通用字段"，视图按状态/待确认角色分
- ⚠️ **批量创建已知问题**：`batchCreateRecords` 在部分身份（UAT）下报 `WrongRequestBody`（实测 2026-08）；批量写失败时**降级为单条循环创建**（create 一次一条），不影响语义
- 负责人字段填人名（来自团队配置角色映射）

## 飞书任务清单（Lark Tasks，推荐轻量团队）

- **双清单约定**：每项目两个任务清单——
  - `{项目名}`：ticket 载体（Story/Bug/Task）
  - `{项目名}-q-item`：Q-items 载体（待确认项）
- **状态**：看板列（section）——ticket 清单配 [待办/进行中/审查中/完成]（可自定义加列）；q-item 清单配 [待回答/已回答/已关闭]
- **字段**：自定义字段（单选：优先级 P0/P1/P2、类型 Story/Bug/Q-item；文本：编号/共识版本/规则编号/回写位置）——**全自动创建**：`custom_fields create`（resource_type=tasklist + resource_id=清单guid），选项在 single_select_setting.options 里定义并返回 guid；**写入任务用 guid 格式**（字段 guid + 选项 guid，不是名称）
- **extra 兜底**：若 custom_fields 不可用（未授权 task:custom_field:write），全部字段可塞 extra JSON（编号/优先级/规则编号/回写位置）——实测 MCP token 可写，不需要额外 scope
- **Q-items 三态映射**：看板列=状态（section_guid）；answered=移动到"已回答"列；closed=完成（completed_at）或移动到"已关闭"列
- 操作：按 `phper666-teamflow-story-to-contract` 适配器（adapters/feishu-task.md）语义执行
- ⚠️ 无评论：回写结论用"描述追加"方案（适配器方案 A）
- 唯一键：task_guid（不要用 task_id 展示编号）
- 能力依据（2026-08 实测）：多状态看板（可加列）✅ / 自定义字段（含优先级推荐字段）✅ / 子任务 ✅ / 甘特图 ✅ / 清单成员权限 ✅

## Jira

- 载体：q-item 子任务类型（挂在父需求下）
- 字段映射到 Jira 自定义字段或描述结构（编号/优先级/共识版本/规则编号等，按团队约定）
- 经办人 = 待确认角色对应的账号（团队配置映射）
- 操作：按 `phper666-teamflow-story-to-contract` 适配器接口的 createItem/addComment/listItems 语义执行
- 状态：open=To Do / answered=In Review（等待复核）/ closed=Done

## TAPD

- 载体：缺陷或需求类型（约定类型名如"待确认项"，建议用缺陷——轻量、不污染需求树）
- 字段：TAPD 自定义字段承载（编号/优先级/待确认角色/共识版本/规则编号/回写位置）；回答放描述/评论
- 状态：open=新建 / answered=处理中（等待复核）/ closed=已关闭
- 操作：按 `phper666-teamflow-story-to-contract` 适配器（adapters/tapd.md）语义执行

## Linear

- 载体：Issue + label `q-item`（编号/角色用 label 或自定义字段）
- 字段：自定义字段（优先级 P0/P1/P2、待确认角色、共识版本、规则编号、回写位置）；回答放 description 或评论
- 状态：open=Backlog/Todo / answered=In Review / closed=Done
- 操作：按 `phper666-teamflow-story-to-contract` 适配器（adapters/linear.md）语义执行；Linear 的 label+状态+优先级结构天然贴合 Q-items 模型

## GitHub

- 载体：Issue + labels（`q-item`、`q-p0`/`q-p1`/`q-p2`、`q-be`/`q-fe`/`q-qa`/`q-pm`）
- 字段：Projects v2 自定义字段承载结构化信息（共识版本/规则编号/回写位置）；回答写 Issue body 或评论
- 状态：open=Open / answered=标签 `q-answered` / closed=Closed
- 操作：按 `phper666-teamflow-story-to-contract` 适配器（adapters/github.md）语义执行；assignee=待确认角色

## OpenProject

- 载体：自定义工作项类型"待确认项"（UI：管理 → 工作包类型 → 新建，类型名为 Q-item 或待确认项）
- 字段：description 结构化承载（编号/共识版本/规则编号/回写位置/回答），优先级用优先级字段（建议 UI 改 P0/P1/P2）
- 状态：open=New / answered=In progress 或自定义"待复核"状态 / closed=Closed
- 操作：按 `phper666-teamflow-story-to-contract` 适配器（adapters/openproject.md，REST API v3）语义执行
- 认证：`OPENPROJECT_URL` + `OPENPROJECT_API_KEY`（API key 唯一可靠，2FA 用户密码认证禁用）

## 状态就绪检查（选择载体后必检）

工作流需要的最小状态集（**双清单共用同一套状态模板**，飞书任务默认列即满足，零配置）：

- **统一 6 态模板**：`Backlog → Todo → In Progress → Verify → Done`，另含 `Blocked`（可进可出）
- **ticket 映射**：完整走 6 态（Backlog=排期池 / Todo=待办 / In Progress=进行中 / Verify=验证审查 / Done=完成 / Blocked=阻塞）
- **Q-items 映射**：`open（待回答）= Todo`、`answered（已回答待复核）= Verify`、`closed（已关闭）= Done`；**Blocked 对 q-item 同样有效**（等外部确认/依赖方回复，解除后回原状态）；**复核不通过 = Verify → Todo 打回**（重新回答，非直接关闭）

各平台检查方式与缺失处理：

| 载体 | 检查方式 | 必需状态是否存在 | 缺失处理 |
|:-----|:---------|:-----------------|:---------|
| 飞书任务清单 | `sections list`（看板列） | **默认 6 列即满足**（Backlog/Blocked/Todo/In Progress/Verify/Done）。⚠️ 新清单自带空名默认列 → **patch 改名利用（改 Todo），不删除**（delete 是 high-risk 需确认） | ✅ 自动改名+建缺列，终态恰好 6 列 |
| 飞书多维表格 | 状态字段单选选项 | 需配置 6 选项 | ✅ 补选项（字段更新） |
| OpenProject | GET /statuses | 默认 14 态已含对应态（New/In progress/On hold/Closed 等） | 用默认映射，不建 |
| Linear | team states | 默认已含 Backlog/Todo/In Progress/Done ✓（Verify 用 label 或自定义） | 用默认映射，不建 |
| Jira | 工作流状态查询（transitions） | 视项目工作流 | ❌ 不能自动建（Jira 工作流是管理配置）→ 提示用户配置 |
| GitHub | labels 检查 | open/closed 原生 ✓；answered 需 label `q-answered` | ✅ 自动建 label |

**执行时机**：phper666-teamflow-workflow-setup Phase 4.5；结果写入团队配置的状态映射段：

```yaml
status_map:
  open:      { platform: "待回答" }   # Q-items 三态 → 载体实际状态
  answered:  { platform: "已回答" }
  closed:    { platform: "已关闭" }
```

**phper666-teamflow-consensus-scan 闭环前检查**：流转前读团队配置 status_map；缺失或未配置 → 提示先跑 phper666-teamflow-workflow-setup 状态就绪检查，不静默失败。

## 双向语义

- 三角色 → PM：扫描发现的问题，待确认角色=PM
- PM → 三角色：PM 建问题给 BE/FE/QA 确认（拆解、评审、写共识时的疑问），待确认角色=对应角色
- 谁回答问题谁填"回答"字段；**回写位置由创建人复核时校验**
