# 技术方案设计（分级）

契约冻结后、实现前的一环：把共识（业务事实）和契约（接口依赖）之间的"how"落成可评审、可对照、可传播的方案。**判定标准一句话：有没有"实现形态的选择"（多条路要选 = 要方案；唯一做法 = 不要）。**

## 判级矩阵

| 级别 | 触发条件 | 要求 |
|:-----|:---------|:-----|
| **复杂** | 跨模块协作、新架构/greenfield、契约变更、状态机、外部系统集成、需求探索判定复杂 | 必出技术方案文档 + 评审；需求探索阶段必产 PRD + 原型（UI 类）；实现走完整实现纪律 |
| **常规** | 单模块改动、CRUD、纯 UI、已有模式的简单延伸、无契约变更 | 跳过方案；轻量实现纪律（lint 单次 + 工程基线三问复核） |
| **安全敏感** | 密钥/权限/支付/资金/数据（在上述任一级之上叠加） | 强制安全扫描（Semgrep 或等价工具 gitleaks/trivy/依赖扫描）；**缺工具必须换等价工具或安装，不得跳过**（见 phper666-teamflow-implement-discipline 工具降级） |

无法判断级别 → 按"有没有实现形态的选择"问一句：有就按复杂出方案，没有就跳过。

## 需求探索（复杂任务前置，必产）

复杂任务在技术方案前完成需求探索：

1. 探索式提问：目标 / 边界 / 约束 / 验收标准逐条确认
2. **产出 PRD**：`docs/prd/<date>-<slug>-prd.md`（需求可回溯的权威文档）
3. **产出原型**（UI 类需求）：交互原型 `docs/prototype/<date>-<slug>-prototype`（与 PRD 同 slug，保证回溯链可对应），验证流程与交互。**UI 类需求 → 确认/更新 `docs/ui/UI规范.md`**（项目级视觉规范：配色/字体/组件/布局，从原型提取）；前端实现时读它做视觉基准
4. PRD + 原型 → 建共识文档（phper666-teamflow-consensus-doc，绑定 PRD/原型链接）→ 契约 → 本方案
5. 回溯链闭合：PRD + 原型 → 共识 → 契约 → 方案 → 实现 → 交付核验（三层含 PRD+原型落实核对）

常规任务可轻量 PRD（可无原型）；内部小任务可不产 PRD。

## 工程基线三问（并入技术方案入口，非独立 Gate）

技术方案判级时顺带检查（复杂/常规都过）：

1. **有 git 吗？** → 无：标记"未做版本控制"，可引导安装或按团队约定处理（不强制）
2. **有脚手架吗？**（package.json 等）→ 无：按技术栈搭最小骨架
3. **有测试框架吗？** → 无：按测试分层搭最小框架（单测必选；集成测试跨模块/外部依赖时必选；e2e 可选）

**技术栈决策**（客户交互）：

```
① 按需求特征推荐候选（1-2 个）+ 推荐理由
② 选项（选择题 + 填空）：
   □ 候选 A（推荐）
   □ 候选 B
   □ 其他：__________（客户自由填写）
③ 客户选择/填写 → 落进技术方案 → 搭脚手架
④ 客户不选也不填 → 技术方案评审时收敛确认
```

技术栈参考：桌面壳 → Electron / Tauri；Web 管理系统 → React/Vue + 主流后端栈；CLI → Node/Python/Rust；存量项目 → 跟随团队既有栈。

**测试分层参考**（按技术栈主流最小选）：

| 层 | 覆盖 | 选择 |
|:---|:-----|:-----|
| 单元测试 | 函数/模块逻辑（分支/边界） | 必选（核心路径） |
| 集成测试 | 模块间协作、外部依赖真实协作（DB/API/文件系统/子进程） | 跨模块或外部依赖时必选 |
| 端到端 e2e | 整条用户链路 | 可选（UI 主链路） |

框架：JS/TS → vitest（+Playwright e2e）；Python → pytest（+Testcontainers）；Java → JUnit（+Testcontainers）；Rust → cargo test；Go → go test（+httptest）。

## 产出

`docs/design/<id>-<模块>-{prd_slug}-design.md`（与 docs/api/ 平级；不引入第二套文档体系）。`<id>` 优先用后端实现子任务 key（如 `scrum-6-壳骨架-m1-design.md`）；无 ticket 时用共识拆解的子需求编号——同一子需求的 design 与 records（docs/records/，`<id>-{prd_slug}-record.md`）必须用同一 id 与同一 prd_slug，回溯链：工作项 → 子任务 → 方案 → 记录。`{prd_slug}` = 需求标识（复杂需求 = PRD 文件名中的 slug，如 `2026-08-14-m1-prd.md` → `m1`；常规需求 = 需求 slug，手给短标识如 `login`），标识该方案由哪个需求生成（一期可多个需求）；**需求标识必填，不留空占位**（`scrum-6-壳骨架-login-design.md`）。**跨期约束**：id 必须含「期」维度——多期项目（M1/M2…）禁止跨期复用编号（任何一期不得沿用其他期的编号段）；建议 `<期>-<子需求>`（`M2-S1`）或按模块用独立编号段（看板期 `B1-B5`），避免同名冲突与语义漂移。

**期编号决策模型（插入/变更需求）**：

- **期编号 = 逻辑分组标识，发布后不重排**（产物编号稳定，重排会连锁改名；历史变更摘要记的期号改不了）
- **排期 = 独立维度，动态调整**（插队/延期正常；改「执行顺序」，不改产物编号）
- **分水岭 = 编号是否已锁**（共识/契约是否已生成）：
  - **已锁**（共识/契约已生成，期编号已定）→ 插入需求**新开期/独立段**（保护已发布产物，不重排）
  - **未锁**（规划未定稿，共识未生成）→ 插入需求**可并入当前/未来期**（规划可调，直接拆子需求）
- **优先级**决定**插队/排队**（高→插队提前做，排期视图调；普通→排队到未来期）
- **性质**决定**新期/增补段**：独立新需求 → 新开期/独立段；对已发布期的重构/增补 → 归该期**增补段**（如 `M2-重构`，需求 slug `m2refactor`），不占新期编号
- **重构区分**（先判重构类别再走期编号决策）：
  - **产品重构**（改变业务行为/规则，用户可见）→ 挂钩原 PRD → 归原期增补段（如 `M2-重构`，需求 slug `m2refactor`），影响原共识/契约 → 走变更传播（phper666-teamflow-change-propagation）
  - **技术重构**（保持行为，改实现，用户不可见）→ 不挂钩原 PRD → 独立散任务（`[模块][重构] <描述>`），无契约变更
- **禁止版本号式编号**：`M2.1`/`M2.2` 与共识文档版本号（v1.x）混淆、语义错位（新需求≠补丁）——增补段用 `M2-<后缀>`（`m2refactor`/`m2add`）
- **独立会话组织**：新期/增补段可开独立会话处理（上下文隔离：新共识/新契约/独立产物编号），当前期独立会话正常推进，互不干扰；增补段需读旧期上下文（M2 文档），产出归 `M2-<后缀>` 不污染 M2 主产物

**分支模型（共享文档 vs 需求专属）**：

- **主分支 = 共享文档**：PRD/原型/共识/规则索引/团队配置——单一事实源，集中维护
- **feature 分支 = 需求专属**：代码 + 契约/设计/记录（`feature/<需求标识>`）——需求标识隔离，合并不冲突
- **需求不做 → feature 分支留着**（代码+文档都不合并），下次做继续，主分支干净
- **改共享文档前** → 先 merge 主分支最新（减少冲突窗口）
- **固定时序**：共识定稿（主分支直推）→ **开 `feature/<需求标识>` 分支** → 契约/设计/记录在 **feature 分支上生成**（story-to-contract 跑在其上）→ 代码实现 → 需求完成合并 / 不做留分支。**契约/设计/记录不直接写主分支**（需求专属，跟代码走分支）

## 内容骨架

```markdown
# <模块>技术方案

> 状态：draft（撰写中）→ frozen（评审通过·冻结，可进实现）

## 1. 背景与范围
- 关联：共识版本 + 规则编号（CON-Rxxx）、契约路径、PRD/原型链接

## 2. 架构决策（含备选）
- 每项决策：方案 A vs 方案 B → 选谁 + 取舍理由
- 不写"该不该用 X"之外的讨论，决策必须给理由

## 3. 模块划分
- 模块清单 + 职责边界 + 依赖方向（复杂需求在此承载依赖结构）

## 4. 关键机制实现形态
- 状态机、原子操作、恢复/重试、并发/事务等高风险点的具体实现方式

## 5. 工程基线
- git/脚手架/测试框架状态 + 技术栈决策结果（三问 + 选择/填空/评审结论）

## 6. 目录/工程结构（如适用）

## 7. 风险与对策
- 已知风险 + 缓解 + 兜底

## 8. 核验记录（交付核验时填写）
- 实现 vs 方案的偏离清单 + 处理结论（有意偏离更新方案+记录理由 / 无意偏离修实现）
```

## 流程位置

1. 契约冻结 → 2. 判级 → 3.（复杂）需求探索（PRD+原型必产）→ 4. 工程基线三问 + 技术栈决策 → 5. 产出方案 + 按评审机制把关 → 6. 实现（phper666-teamflow-implement-discipline）→ 7. 交付核验对照本方案（设计核验，见 phper666-teamflow-story-to-contract 交付核验模式 ①）

## 纪律

- **角色中立**：产出由当前实现角色完成；评审按「评审机制」配置走（**读 `docs/spec/团队配置.md` 的「评审机制」两级表：需求级覆盖 > 项目级默认 > 默认 self-check**），不绑定任何平台特定角色
- **评审机制三选一**（`docs/spec/团队配置.md` 配置，未配置 → 默认 self-check）：
  - **gate**：多人团队，方案走正式 Gate 评审（评审记录留痕：评审人/机制 + 日期 + 结论）
  - **self-check**：solo/小团队，AI 自查通过即 frozen（默认值）
  - **review**：方案先给用户/指定人 review 再 frozen
- 方案只写当前变更需要的；不写脚手架式未来设计（YAGNI）
- 评审不过 → 修订方案再评审，不得带病进实现；评审通过 → 状态置 frozen 并在「评审记录」留痕（评审人/机制 + 日期 + 结论），未 frozen 不得进实现
- 方案随实现演进：有意的实现偏离 → 显式更新方案文档 + 记录理由，不静默漂移；架构/机制级重大偏离 → 回 draft 重新评审再继续
- 可复用的设计决策/取舍 → 候选 lessons（见 phper666-teamflow-lesson-deposit 三硬标准）
- 技术栈/测试框架决策落进方案后即为准，实现不擅自更换
