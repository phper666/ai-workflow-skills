# 共识文档生命周期（PM 侧）

管理模块共识文档的完整上游生命周期：**建立 → 发布基线 → 评审就绪 → 拆解子需求**。共识文档回答"业务应该是什么"，是唯一的业务事实源；下游所有产物（待确认项、子需求、契约、测试）都必须绑定它的版本和规则编号。

模板见 `references/模板-共识文档.md`（15 节骨架，含第 3 节领域术语表）；变更摘要模板在 `phper666-teamflow-change-propagation/references/模板-变更摘要.md`（单一源）；多版本迭代/归档/分支约定见 `references/多版本策略.md`（正常迭代不归档，归档只在替换式大变更）。

## Phase 0：需求探索（复杂任务前置，必产）

**输入**：模糊需求（"我想要 X"、"加个 Y 功能"）。

1. 判级：按 phper666-teamflow-tech-design 判级矩阵判定复杂/常规（跨模块、新架构、契约变更、状态机、外部系统集成 = 复杂）
2. 复杂任务 → 探索式提问（目标 / 边界 / 约束 / 验收标准逐条确认）
3. **产出 PRD**：`docs/prd/<date>-<slug>-prd.md`（需求可回溯的权威文档）
4. **产出原型**（UI 类需求）：交互原型（`docs/prototype/`），验证流程与交互
5. 常规任务 → 可轻量 PRD（可无原型）；内部小任务可不产 PRD

**回溯链**：PRD + 原型 → Phase 1 建共识（绑定链接）→ 契约 → 技术方案 → 实现 → 交付核验（含 PRD+原型落实核对）。PRD/原型缺失则需求无法回溯，复杂任务禁止跳过。

**Phase 0 完成后（过渡指令）**：PRD/原型确认后，**直接进入 Phase 1 建立共识文档**（从 PRD/原型提取整理），不要询问用户「下一步跑扫描还是发布基线」——扫描与基线都在 Phase 1 之后，顺序固定：建共识 → 用户确认 → 发布基线 → 扫描。若用户主动问顺序，按此固定顺序回答，不提供并列选项。

## Phase 1：建立共识文档

**输入**：PRD、原型链接、已有共识（更新场景）、或仅口头业务描述。

1. **共识文档命名与需求标识**：命名 `共识-{模块}-{需求标识}.md`（如 `共识-桌面壳-m1.md`、`共识-桌面壳-login.md`）。**需求标识** = 复杂需求用 PRD slug（PRD 文件名 slug，如 `2026-08-14-m1-prd.md` → `m1`），常规需求用需求 slug（手给短标识如 `login`）。无 PRD 的常规需求 → 建共识时手给需求 slug，检测 `docs/` 已用 slug 避免重复（有 → 改 `login2`）；有 PRD → 需求标识 = PRD slug（PRD 文件名天然唯一）。同模块不同需求文档名不冲突，各需求独立隔离。
2. 有 PRD/原型 → 读取并按 15 节骨架**提取整理**，不重写、不翻译成新叙事。PRD 是创作态，共识是事实源。
3. 纯口头 → 按 15 节逐节采集，每节确认后再进下一节。
4. 规则编号：为关键业务规则建立稳定编号（`CON-R-{需求标识}-{序号}` 起，如 `CON-R-m1-001`、`CON-R-login-001`——**各需求独立编号域，不撞号**；查 `docs/spec/规则索引.md` 现有编号避免冲突），每条规则记录：描述 / 来源 / 当前结论 / 变更状态。**存量 `CON-R001` 历史编号不重排**（新规则用新格式）。
5. 领域术语表采集：从 PRD/原型/讨论中提取候选业务词 → 挑出"重要 + 有歧义风险"的 → 每个词记录：定义 + 出处（章节/PRD 位置）→ 写入共识文档"领域术语表"章节。评审时发现歧义 → 补条目。**术语表共享（跨模块）**：跨模块共享的术语在**任一模块共识定义（主模块）**，其他模块引用「术语：见 共识-<主模块> §3」，**不重复定义**（避免两模块术语不一致）；变更主模块术语 → 走跨模块变更传播（phper666-teamflow-change-propagation 跨模块协调）通知引用模块。
6. 显式记录三样负面清单：**未决项**（PRD 里的"待定/稍后/未确认"字眼自动抓取登记）、**适用范围**（管哪些模块、不碰哪些）、**不做事项**（明确排除的需求）。没写这三样，别人会默认"没写=可以做"。
7. 检查自相矛盾：同一事实两处说法不一致时，停下来问用户，不自行取舍。

**TBD 纪律**：业务事实不确定就标未决项，**禁止编造**。你追问得越细，共识越准；PRD 有洞，共识就显式标洞，而不是帮你补。

**Phase 1 完成后（过渡指令）**：向用户展示共识文档摘要（结构 / 规则编号 / 未决项 / 不做事项），询问确认。确认后进入 Phase 2 发布基线（自动生成扫描通知），再进入扫描。**顺序固定：基线 → 扫描**，不提供「先扫描」选项——扫描输入必须是基线版本，Q-items 需绑定版本号。

## Phase 2：发布共识基线

用户确认文档内容后：

1. 升版本号 + 更新时间（版本不可歧义，如 v1.0；禁止 `final_v2_最终版` 式命名）
2. 关联原型、Jira Epic/父需求、来源材料链接
3. 生成扫描通知：范围 + 截止时间（内容：请 BE/FE/QA 在 X 前完成扫描）
4. 版本记录写入 `docs/spec/变更摘要-<模块>.md`（L2 详情：版本行 + 本版本规则变化条目，模板见 phper666-teamflow-change-propagation references），同时双写一行索引到 `docs/spec/变更摘要.md`（L1）——**版本记录的详情事实源在 L2 模块文件**；文档附录版本记录表只留一行指针（`版本 | 日期 | 变更摘要条目引用`），不复制详情

**产出**：共识基线版本 + 扫描通知。后续所有问题必须绑定此版本。

## Phase 3：评审就绪检查（Gate A）

会前模式：用户说"评审前检查"时执行，输出"可以开评审 / 还差 X 项"：

- [ ] 结构完整，无明显自相矛盾
- [ ] 关键规则可被唯一引用（编号存在且索引登记）
- [ ] 未决项有登记（不要求清零，但必须显式）
- [ ] P0 待确认项已清零（查 Q-items 载体，见 phper666-teamflow-consensus-scan）
- [ ] 文档版本可追踪
- [ ] 适用范围 / 不做事项已写
- [ ] 本版本有规则变化时，`docs/spec/变更摘要-<模块>.md` 已生成对应条目（版本行 + 规则条目，见 phper666-teamflow-change-propagation 模板）

会后模式：用户说"评审结论回写"时执行：
1. 评审中确定的结论写入正文（不留在会议纪要）
2. 会议新发现的问题 → 走待确认闭环（phper666-teamflow-consensus-scan），不例外
3. 升版本 + 输出结构化变更摘要（`docs/spec/变更摘要-<模块>.md` 追加条目，模板见 `phper666-teamflow-change-propagation/references/模板-变更摘要.md`）

**评审的作用是验证已成形共识，不是第一次发现问题**。会前发现问题多，说明 Phase 1 或扫描没做完，先回去补，不硬开评审。

## Phase 4：拆解模块子需求

用户确认基线稳定后（Gate A 通过）：

1. 按模块拆子需求（Story/父需求级），每个子需求绑定：共识文档版本 + 引用规则编号 + 验收标准（可测试）+ 不做事项 + **来源 PRD**（该子需求由哪个 PRD 生成，一期可多个 PRD）
2. 标注依赖：依赖模块 / 第三方 / 跨团队协调项
3. 范围检查：每个子需求可由一个交付周期覆盖
4. **只建 PM 侧的子需求**。BE/FE/QA 各自的交付任务由各角色自己建（BE 用 phper666-teamflow-story-to-contract 的创建流程，FE/QA 用各自流程），不替别人建任务

**产出落地动作（Gate B 通过前必须完成，缺一不得进入契约阶段）**：

1. **子需求清单写入共识文档附录**（§14：编号/验收标准/规则绑定/依赖/顺序/**来源 PRD**）
2. **PM 侧子需求 ticket 化**：写入 ticket 载体（类型按载体映射：Story / User story / 需求；字段：优先级、规则编号），记录 ticket id 到附录清单。**ticket 名称两类**：
   - **子需求类**（拆解的可交付单元，有编号）：`[模块][需求标识] <子需求编号> <名称>`（如 `[Hull][m1] S1 壳骨架与进程管理`；**需求标识必填** = 复杂需求用 PRD slug（`m1`，来自 `2026-08-14-m1-prd.md`），常规需求用需求 slug（手给短标识如 `login`）——同期同模块多需求时区分来源，不留空占位）
   - **散任务类**（无编号执行项：Bug/优化/调研/测试/文档/重构/任务…）：`[模块][类型] <描述>`（如 `[Hull][Bug] 升级回滚后残留检测误判`；类型用通用词，模块前缀复用，给人看的列表一眼区分归属/类型）
   **ticket 描述 = 快照 + 指针**：展开共识关键验收点（2-5 行可测试条目）+ 一行声明「依据：共识 vX.Y §A.B；冲突时以共识为准」——快照是生成时的投影，不重复共识全文；共识变更时只改共识正文，不回写历史 ticket 快照
3. **自查**：验收可测试 ✓ / 规则绑定 ✓ / 依赖标注 ✓ / 单交付周期可覆盖 ✓
4. **产出确认汇报**：清单表 + 载体位置 + Gate B 就绪

**产出**：模块子需求清单（绑定共识版本+规则编号，ticket 已落载体），满足 Gate B（需求就绪）。

> **下游衔接**：子需求进入契约阶段（phper666-teamflow-story-to-contract）→ 契约复核通过（冻结）后，复杂/高风险子需求须先按 `phper666-teamflow-tech-design` 产出技术方案（docs/design/）再实现；常规/简单直接实现。技术方案绑定共识版本 + 规则编号。

## 纪律

- **落载体才算完成**：每个阶段"讨论定稿"不是产出——**落载体（文档/清单/ticket）才是**；未落载体不得进入下一阶段（Gate A/B/C 的落地动作是强制检查点，不存在"讨论完就跳下一步"）
- 共识文档只维护当前有效结论；历史结论进变更记录，不累积删除线
- 任何业务结论变化 = 升版本 + 变更摘要（这是 phper666-teamflow-change-propagation 的输入）
- 未决项登记处与 Q-items 载体保持同步（共识里登记了 → 待确认闭环里要有对应条目）
- 文档结构以模板为准；确实不需要的章节写"本模块不涉及"，不删除章节（保结构稳定）
