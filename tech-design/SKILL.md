# 技术方案设计（分级）

契约冻结后、实现前的一环：把共识（业务事实）和契约（接口依赖）之间的"how"落成可评审、可对照、可传播的方案。**判定标准一句话：有没有"实现形态的选择"（多条路要选 = 要方案；唯一做法 = 不要）。**

## 分级

| 级别 | 特征 | 动作 |
|:-----|:-----|:-----|
| 复杂/高风险 | 状态机、安全/权限/资金/数据、多模块协作、greenfield 架构、外部系统集成 | **必出**技术方案文档 + 评审 |
| 常规 | CRUD、单模块改动、纯 UI、已有模式的简单延伸 | 跳过，技术决策留在契约/代码 review |
| 简单 | 一行改动、配置调整 | 跳过 |

无法判断级别 → 按"有没有实现形态的选择"问一句：有就按复杂出方案，没有就跳过。

## 产出

`docs/design/<子需求id>-<模块>-design.md`（与 docs/api/ 平级；不引入第二套文档体系）

## 内容骨架

```markdown
# <模块>技术方案

## 1. 背景与范围
- 关联：共识版本 + 规则编号（CON-Rxxx）、契约路径

## 2. 架构决策（含备选）
- 每项决策：方案 A vs 方案 B → 选谁 + 取舍理由
- 不写"该不该用 X"之外的讨论，决策必须给理由

## 3. 模块划分
- 模块清单 + 职责边界 + 依赖方向

## 4. 关键机制实现形态
- 状态机、原子操作、恢复/重试、并发/事务等高风险点的具体实现方式

## 5. 目录/工程结构（如适用）

## 6. 风险与对策
- 已知风险 + 缓解 + 兜底

## 7. 核验记录（交付核验时填写）
- 实现 vs 方案的偏离清单 + 处理结论（有意偏离更新方案+记录理由 / 无意偏离修实现）
```

## 流程位置

1. 契约冻结 → 2. 判定级别 → 3.（复杂）产出方案 + 团队既有评审机制把关 → 4. 实现 → 5. 交付核验时对照本方案（设计核验，见 story-to-contract 交付核验模式 ①）

## 纪律

- **角色中立**：产出由当前实现角色完成；评审走团队既有机制（有评审文化的团队走 Gate，solo/小团队自查+review 兜底），不绑定任何平台特定角色
- 方案只写当前变更需要的；不写脚手架式未来设计（YAGNI）
- 评审不过 → 修订方案再评审，不得带病进实现
- 方案随实现演进：有意的实现偏离 → 显式更新方案文档 + 记录理由，不静默漂移
- 可复用的设计决策/取舍 → 候选 lessons（见 lesson-deposit 三硬标准）
